4. CORE RELATIONSHIP GRAPH
============================================================

Use these relationships when necessary:


users
    |
    | user_id
    v
sessions
    |
    | session_id
    v
user_behavior_logs
    |
    | product_id
    v
products
    |
    +---- brand_id ------> brands
    |
    +---- category_id ---> categories
    |
    +---- seller_id -----> sellers


sessions
    |
    +---- city_id -------> cities


products
    |
    | products.id = comments.product_id
    v
comments
    |
    | comments.id = comment_aspects.comment_id
    v
comment_aspects

IMPORTANT JOIN RULE:

To connect behavior logs to users:

public.user_behavior_logs
    -> public.sessions
    -> public.users

Join:
user_behavior_logs.session_id = sessions.session_id
sessions.user_id = users.user_id

To connect behavior logs to city:

public.user_behavior_logs
    -> public.sessions
    -> public.cities

Join:sessions.city_id = cities.city_id

To connect behavior logs to brand/category/seller:

public.user_behavior_logs
    -> public.products
    -> public.brands/categories/sellers

Join:
user_behavior_logs.product_id = products.id
products.brand_id = brands.brand_id
products.category_id = categories.category_id
products.seller_id = sellers.seller_id

To connect comments to product:

public.comments
    -> public.products

Join:comments.product_id = products.id

To connect comment aspects:

public.comment_aspects
    -> public.comments

Join:comment_aspects.comment_id = comments.id
============================================================
TABLE GRAIN RULES
============================================================
Always preserve the original grain of every table.
Table grains:
public.user_behavior_logs:event level (one row per behavior event)
public.comments:comment level (one row per comment)
public.comment_aspects:aspect level (many rows per comment)
analytics.feature_user:user level
analytics.feature_product:product level
analytics.feature_brand_sentiment:brand level
analytics.feature_category_sentiment:category level
analytics.feature_product_sentiment:product level
analytics.feature_user_product:user-product level
analytics.feature_user_category:user-category level
analytics.feature_time:hour-weekday level

Analytics tables contain precomputed aggregated features, not raw events.

JOIN AND AGGREGATION RULES:
Before aggregating after JOIN:
1. Check whether the JOIN changes the grain.
2. Prevent duplication of higher-grain metrics.
3. Use DISTINCT counting or pre-aggregation when required.

Prefer:
- existing KPI/feature metrics
- pre-aggregation before JOIN
- COUNT(DISTINCT ...)
- highest available grain table
Never SUM, AVG, or COUNT metrics from an aggregated table after joining it with a lower-grain table unless duplication is explicitly handled.

6. KPI OBJECTS (VIEWS + TABLES)
============================================================

The KPI schema contains business-level precomputed metrics.

KPI objects can be:
- Views
- Tables

If a requested metric exists in KPI objects, always prefer KPI objects.

Never recalculate KPI metrics from lower-grain tables unless explicitly requested.

Always respect KPI object grain.

kpi.global_funnel
============================================================
Purpose:Global funnel metrics.
Grain:ONE ROW PER PLATFORM

Columns:
total_views
total_carts
total_purchases
total_removes
view_to_cart_pct
cart_to_purchase_pct
overall_conversion_pct
cart_abandonment_pct

Metrics:
view_to_cart_pct = total_carts / total_views * 100
cart_to_purchase_pct = total_purchases / total_carts * 100
overall_conversion_pct = total_purchases / total_views * 100
cart_abandonment_pct = (total_carts - total_purchases) / total_carts * 100
============================================================
kpi.product_360
============================================================
Purpose:Complete product performance view.
Grain:ONE ROW PER PRODUCT

Columns:
product_id
title_fa
price
total_views
total_purchases
total_revenue
conversion_rate
comment_count
star_rating
positive_sentiment_pct
sentiment_score
managerial_action_tag

Rules:
total_revenue definition:
total_revenue =total_purchases * current product price
This metric is calculated inside the KPI view.
Do not recalculate from raw behavior logs unless explicitly requested.
Metrics:
conversion_rate =
total_purchases / total_views * 100

positive_sentiment_pct =
positive_aspect_ratio * 100

sentiment_score =
(positive_aspect_ratio - negative_aspect_ratio) * 100

managerial_action_tag values:
Hero Product
High Traffic, Low Conversion
High Risk
Needs Reviews
Normal

kpi.user_segments
============================================================
Purpose:User behavioral segmentation.
Grain:ONE ROW PER USER

Columns:
user_id
active_days
total_views
total_purchases
total_spend
user_segment
user_conversion_pct

Metrics:
user_conversion_pct =
total_purchases / total_views * 100

Segments:

VIP Customer:
total_purchases >= 5
AND total_spend > 10000000

Returning Customer:
total_purchases > 1
AND total_purchases < 5

One-Time Buyer:total_purchases = 1
Window Shopper:
total_purchases = 0
AND total_views > 20
Low Engagement:remaining users
